<Tags items={['Flyway · migrations', 'Spring Session JDBC', 'daily backup · 14 days', 'Coolify · docker compose']} />

The web app and the API share the same origin: nginx serves the PWA and proxies `/api`, so there's no CORS and the session cookie can be `SameSite=Strict`. No service in the production compose file publishes ports; only `web` receives traffic, through Traefik.

Each calculation runs where it makes the most sense. Trend weight, body composition, adaptive energy expenditure and the weekly check-in live in the Java backend as the source of truth. Workout load progression runs only in the TypeScript frontend, so the next set is suggested instantly, without waiting on the network.

</Section>

<Section n="03" title="Technical decisions">

<Cards>
  <Card title="Pure engines, tested against fixtures">
    Trend, body composition, energy expenditure and check-in are pure functions with no I/O. The trend and body composition fixtures come from an independent JavaScript implementation that acts as a second opinion on the Java math.
  </Card>
  <Card title="A calorie target that adapts">
    Daily expenditure is estimated from logged intake and weight change over a 21-day window. The weekly check-in proposes a new target with smoothing and a step cap, and I accept, edit or decline it.
  </Card>
  <Card title="Workouts that never lose a set">
    Each set is saved to a local draft and sent with a client-generated ID to idempotent routes. If the network drops, it retries with exponential backoff (2–60 s). Retries never duplicate, and a 401 prompts a login and then resumes sending.
  </Card>
  <Card title="Immutable history">
    Every food log stores a snapshot of the nutrition values. Fixing a food's label doesn't change past days unless I explicitly ask for a recalculation.
  </Card>
</Cards>

<Section n="04" title="A decision made by simulation">

How you measure weight change has a big impact on the proposed target. Instead of eyeballing it, I wrote an integration test that simulates weeks of dieting with early water loss, scale noise and missed weigh-ins across 30 random seeds, and compared five variants of the calculation:

| Variant | Mean error (kcal) | Bias (kcal) | Worst swing between check-ins | Seeds with a jump > 100 kcal |
|---|---|---|---|---|
| Smoothed trend | 121 | +107 | 130 | 2 |
| Regression on raw weigh-ins | 96 | +21 | 150 | 15 |
| **Regression + ±70 kcal cap** | **95** | **+21** | **70** | **0** |
| Regression, 28-day window | 92 | +42 | 130 | 4 |
| Average of both | 90 | +57 | 140 | 5 |

The criterion: at most 3 seeds with a jump above 100 kcal and, among those, the lowest bias. The winner became the code's default, and the test fails if anyone changes the default without the simulation agreeing.

</Section>

<Section n="05" title="Security">

The app stores health data, so authentication was the first thing to be finished:

- **No sign-up.** The single user is created on first boot from an argon2id hash generated outside the app.
- **Mandatory 2FA from the first login.** TOTP with the secret encrypted with AES-256-GCM, protection against code replay, and 10 recovery codes stored as hashes.
- **Database-backed sessions** (Spring Session JDBC), an `HttpOnly` and `SameSite=Strict` cookie, a new ID on every login, and double-submit CSRF on every mutation.
- **Brute force:** 5 failures every 15 minutes per IP and per user returns 429 with `Retry-After`.
- **Edge:** strict CSP, HSTS, `X-Frame-Options: DENY`. Logs never record request payloads, only method, route, status and timing.

</Section>

<Section n="06" title="Quality and deployment">

- **77 API tests** with JUnit and Testcontainers (a real MySQL) and **30 frontend tests** with Vitest, covering load progression and the workout draft.
- **End-to-end browser test:** start a workout, cut the network, close and reopen the app offline, bring the network back and check in the API that no set was duplicated.
- **Deployed on Coolify** with `docker-compose.prod.yml`: a dedicated MySQL, daily backups with 14-day retention and a documented restore procedure.
- **Installable PWA**, with a service worker only for static assets. Data always comes from the network.
